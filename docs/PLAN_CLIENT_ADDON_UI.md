# План реализации клиентского аддона для трансмогрификации

## 1. Цель

Добавить для WoW 3.3.5a клиентский аддон с отдельным интерфейсом
трансмогрификации и локальным предпросмотром на модели персонажа.

Серверный модуль продолжает отвечать за:

- доступность внешности в коллекции;
- совместимость исходного предмета с целевым слотом;
- стоимость операции;
- списание денег;
- применение и удаление трансмогрификации;
- сохранение результата в базе данных.

Аддон отвечает только за отображение данных, локальный предпросмотр и отправку
пользовательских действий на сервер. Доверять данным, пришедшим от аддона,
нельзя.

## 2. Рекомендуемый пользовательский сценарий

1. Игрок взаимодействует с существующим NPC-трансмогрификатором.
2. Если аддон установлен и подтвердил совместимую версию протокола, сервер
   открывает интерфейс аддона.
3. Аддон показывает экипированные слоты и модель персонажа.
4. При выборе слота аддон запрашивает доступные для него внешности.
5. Игрок выбирает внешность и сразу видит её через `DressUpModel:TryOn()`.
6. По кнопке «Применить» сервер повторно выполняет все проверки и применяет
   внешний вид через существующую серверную логику.
7. Игрок получает подтверждение либо локализованную ошибку.
8. Если аддона нет или версия протокола несовместима, продолжает работать
   текущее gossip-меню.

Дополнительно оставить slash-команду `/transmog` для повторного открытия окна,
но разрешать применение только при активной серверной сессии взаимодействия с
NPC. Это сохраняет текущее ограничение доступа к услуге.

## 3. Предварительная проверка HD-клиента

До разработки полного интерфейса сделать минимальный тестовый аддон:

- создать `DressUpModel`;
- вызвать `SetUnit("player")`;
- применить несколько предметов через `TryOn(itemLink)`;
- проверить броню и оружие;
- проверить последовательное наложение нескольких предметов;
- проверить поворот, масштабирование и сброс модели.

Если `DressUpModel:TryOn()` не работает на используемой сборке HD-клиента,
полноценный аддон не решит проблему предпросмотра без клиентского патча. В этом
случае серверный протокол и каталог всё ещё можно реализовать, но модель следует
отключить либо заменить отображением иконок.

## 4. Архитектура

### 4.1. Клиентская часть

Рекомендуемая структура:

```text
client/Transmog/
├── Transmog.toc
├── Core.lua
├── Protocol.lua
├── ModelPreview.lua
├── Collection.lua
├── UI.lua
└── Localization.lua
```

Для MVP не использовать внешние UI-фреймворки. Стандартного API WoW 3.3.5a
достаточно, а отсутствие зависимостей упростит установку и поддержку.

Обязанности компонентов:

- `Core.lua` — инициализация, события, slash-команда и состояние окна;
- `Protocol.lua` — сериализация сообщений, проверка версии и сборка чанков;
- `ModelPreview.lua` — работа с `DressUpModel`, сброс и применение набора;
- `Collection.lua` — кэш item ID, фильтрация и пагинация;
- `UI.lua` — список слотов, сетка внешностей, поиск и кнопки действий;
- `Localization.lua` — как минимум `enUS` и `ruRU`, с fallback на `enUS`.

### 4.2. Серверная часть

Добавить отдельный обработчик протокола, не смешивая разбор сообщений с UI-кодом
существующего NPC:

```text
src/
├── TransmogAddonProtocol.h
└── TransmogAddonProtocol.cpp
```

Обработчик должен:

- распознавать только собственный префикс сообщений;
- выполнять handshake и проверять версию протокола;
- создавать короткоживущую сессию при взаимодействии с NPC;
- отдавать данные порциями;
- ограничивать частоту запросов;
- валидировать все команды;
- вызывать существующие методы `Transmogrification`, а не дублировать правила.

В `transmog_scripts.cpp` останется интеграция с NPC и существующий fallback.
Регистрацию нового серверного скрипта добавить в `transmog_loader.cpp`.

## 5. Транспорт и протокол

### 5.1. Транспорт

Использовать addon channel AzerothCore (`LANG_ADDON`) через whisper самому себе.
Он уже поддерживается ядром и не засоряет обычный чат.

Не использовать обычные скрытые команды чата как основной API. Они хуже
подходят для порционной передачи данных и смешивают пользовательские команды с
машинным протоколом.

### 5.2. Ограничения

- одно addon-сообщение должно укладываться в лимит клиента, не более 255 байт;
- списки передаются чанками;
- каждому запросу присваивается короткий числовой `requestId`;
- крупные ответы содержат номер чанка и общее количество чанков;
- клиент отбрасывает ответы неизвестной версии и устаревшие ответы;
- сервер ограничивает количество запросов от одного игрока.

Для протокола использовать компактный текстовый формат с разделителем `\t`.
JSON для WoW 3.3.5a потребует дополнительной библиотеки и даст лишний объём.

### 5.3. Версия 1 протокола

Префикс: `AC_TRANSMOG`.

Клиентские сообщения:

```text
HELLO\t1
SLOTS\t<requestId>
LIST\t<requestId>\t<slot>\t<page>\t<search>
APPLY\t<requestId>\t<sessionId>\t<slot>\t<itemEntry>
REMOVE\t<requestId>\t<sessionId>\t<slot>
CLOSE\t<sessionId>
```

Серверные сообщения:

```text
HELLO_OK\t1\t<featureFlags>
OPEN\t<sessionId>\t<expiresAt>
SLOTS\t<requestId>\t<data>
LIST_BEGIN\t<requestId>\t<total>\t<pages>
LIST_CHUNK\t<requestId>\t<chunk>\t<chunks>\t<itemEntries>
LIST_END\t<requestId>
RESULT\t<requestId>\tOK\t<slot>\t<itemEntry>\t<money>
RESULT\t<requestId>\tERROR\t<errorCode>
COLLECTED\t<itemEntry>
CLOSE\t<reason>
```

Точные имена сообщений можно скорректировать при реализации, но версия и
границы ответственности должны сохраниться.

## 6. Серверная сессия взаимодействия

Для каждого игрока хранить только временное состояние в памяти:

- `sessionId`;
- GUID NPC;
- время истечения;
- время последнего запроса;
- согласованную версию протокола.

Сессию создавать только после реального `OnGossipHello` у
`npc_transmogrifier`. Перед `APPLY` и `REMOVE` проверять:

- модуль включён;
- сессия существует и не истекла;
- `sessionId` совпадает;
- NPC существует, доступен игроку и находится в разрешённой дистанции;
- игрок не находится в состоянии, запрещающем операцию;
- целевой слот существует и содержит предмет;
- внешний вид находится в коллекции аккаунта;
- внешний вид подходит целевому предмету;
- у игрока достаточно денег.

Сессию закрывать при logout, уходе от NPC, истечении TTL или явном `CLOSE`.
Рекомендуемый TTL — 60 секунд с продлением после валидного запроса.

## 7. Получение списка внешностей

Рекомендуется не отправлять всю коллекцию при каждом открытии окна. Сервер должен
возвращать уже отфильтрованные данные для выбранного экипированного слота.

Порядок обработки `LIST`:

1. Получить предмет в выбранном equipment slot.
2. Найти коллекцию аккаунта в существующем `collectionCache`.
3. Для каждого item ID получить `ItemTemplate`.
4. Использовать существующую проверку совместимости.
5. Применить серверный поиск по локализованному имени, если передана строка.
6. Отсортировать по качеству и имени согласно действующей конфигурации.
7. Вернуть только запрошенную страницу.

Рекомендуемый размер страницы для MVP — 60 элементов. Клиент получает item ID и
сам использует клиентский item cache для имени, иконки, качества и ссылки.

Если HD-клиент содержит нестандартные предметы, отсутствующие в клиентском DBC,
аддон должен показывать заглушку вместо ошибки.

## 8. Применение и удаление внешности

Существующую операцию трансмогрификации нужно вынести в переиспользуемый
серверный метод, если текущая функция `PerformTransmogrification()` слишком
связана с gossip-контекстом.

Метод должен возвращать структурированный результат:

```cpp
struct TransmogOperationResult
{
    bool success;
    TransmogStrings message;
    uint32 resultingEntry;
    uint32 remainingMoney;
};
```

Не переносить расчёт цены или правила совместимости в Lua. Клиент может
показывать предварительную цену, но окончательная сумма всегда определяется
сервером.

После успешной операции сервер отправляет `RESULT OK`, а аддон обновляет текущий
слот и модель. После ошибки аддон показывает сообщение и запрашивает актуальные
данные слота при необходимости.

## 9. Интеграция с NPC и fallback

На первом этапе рекомендуется сохранить текущее поведение NPC без изменений для
игроков без аддона.

После успешного `HELLO` сервер запоминает наличие аддона до конца сессии игрока.
При открытии NPC:

- с совместимым аддоном — отправляется `OPEN`, gossip можно закрыть;
- без аддона — открывается существующее gossip-меню;
- при ошибке протокола — открывается gossip и выводится необязательное
  уведомление о несовместимой версии аддона.

Не делать наличие аддона обязательным, пока новый интерфейс не проверен на всех
поддерживаемых клиентах.

## 10. UI для MVP

Окно должно содержать:

- модель персонажа;
- вертикальный список поддерживаемых equipment slots;
- сетку иконок внешностей;
- поле поиска;
- индикатор страниц;
- цену операции;
- кнопки «Применить», «Снять трансмог» и «Закрыть»;
- область статуса или ошибок.

Поведение:

- один клик по внешности — локальный предпросмотр;
- tooltip при наведении — стандартный `GameTooltip:SetHyperlink()`;
- двойной клик или кнопка — применение с подтверждением при ненулевой цене;
- Escape — закрытие окна;
- смена страницы не сбрасывает выбранную внешность без необходимости;
- во время запроса кнопка применения блокируется;
- повторный запрос с тем же `requestId` не должен повторно списывать деньги.

Сохранённые комплекты не включать в первый MVP. Их лучше добавить после
стабилизации одиночных операций, используя тот же протокол.

## 11. Безопасность и устойчивость

- Никогда не принимать цену от клиента.
- Никогда не считать переданный item ID доказательством владения внешностью.
- Не разрешать применение без подходящего экипированного целевого предмета.
- Защитить повторный `APPLY` от двойного списания денег.
- Ограничить длину поиска и разрешённые символы.
- Проверять числовые поля без исключений и переполнения.
- Ограничить частоту `LIST` и `APPLY` отдельно.
- Не логировать каждое нормальное addon-сообщение на production-уровне.
- Добавить debug-логирование под отдельной настройкой конфигурации.
- Не выполнять SQL в обработчиках просмотра списка; использовать существующий
  in-memory cache.

## 12. Конфигурация

Добавить минимальные параметры:

```ini
Transmogrification.Addon.Enabled = 1
Transmogrification.Addon.PreferInterface = 1
Transmogrification.Addon.SessionTtlSeconds = 60
Transmogrification.Addon.PageSize = 60
Transmogrification.Addon.Debug = 0
```

Не добавлять отдельные настройки для каждого элемента UI: клиентские визуальные
настройки следует хранить в `SavedVariables` аддона.

## 13. Этапы реализации

### Этап 0. Проверка технической возможности

- Создать минимальный аддон с `DressUpModel`.
- Проверить `TryOn()` на целевом HD-клиенте.
- Зафиксировать особенности API этой клиентской сборки.

Результат: подтверждён работающий локальный предпросмотр либо принято решение о
режиме без модели.

### Этап 1. Каркас аддона и handshake

- Добавить `.toc` с версией интерфейса 30300.
- Зарегистрировать addon prefix.
- Реализовать `HELLO`/`HELLO_OK`.
- Добавить slash-команду и простое диагностическое окно.
- Добавить серверный обработчик сообщений и конфигурацию.

Результат: клиент и сервер согласовывают версию, ошибки не попадают в обычный
чат.

### Этап 2. Открытие от NPC

- Создавать серверную сессию в обработчике NPC.
- Отправлять `OPEN` совместимому аддону.
- Сохранить gossip fallback.
- Реализовать TTL, закрытие и проверку дистанции.

Результат: окно аддона открывается только в допустимом контексте.

### Этап 3. Каталог внешностей

- Реализовать `SLOTS` и `LIST`.
- Добавить серверную фильтрацию, поиск, сортировку и страницы.
- Реализовать сборку чанков на клиенте.
- Показать сетку иконок, tooltips и состояния загрузки.

Результат: игрок видит только совместимые внешности из своей коллекции.

### Этап 4. Предпросмотр

- Добавить модель персонажа.
- Реализовать применение выбранной внешности к модели.
- Корректно восстанавливать остальные экипированные предметы.
- Добавить сброс, вращение и масштабирование.

Результат: выбор внешности не меняет персонажа на сервере, но сразу виден в UI.

### Этап 5. Применение и удаление

- Выделить переиспользуемую серверную операцию.
- Реализовать `APPLY`, `REMOVE` и структурированные результаты.
- Добавить защиту от повторной операции.
- Обновлять UI, деньги и модель после результата.

Результат: основной сценарий полностью работает без выбора внешности в gossip.

### Этап 6. Полировка и совместимость

- Добавить `ruRU` и `enUS`.
- Проверить поведение без аддона и с несовместимой версией.
- Проверить нестандартные HD-модели, оружие и скрытие слотов.
- Добавить инструкцию установки и troubleshooting.
- Провести нагрузочную проверку больших коллекций.

Результат: MVP готов к ограниченному production-тестированию.

### Этап 7. Дополнительные возможности

После стабилизации MVP:

- сохранённые комплекты;
- предпросмотр полного комплекта;
- фильтры по качеству и типу;
- список недавно использованных внешностей;
- избранное в `SavedVariables`;
- уведомления `COLLECTED` при пополнении коллекции;
- режим переносного NPC.

## 14. Тестирование

### Серверные проверки

- валидное применение внешности;
- несовместимый тип брони или оружия;
- отсутствующая в коллекции внешность;
- пустой или неподдерживаемый слот;
- недостаточно денег;
- просроченная или поддельная сессия;
- NPC слишком далеко;
- повтор одного `requestId`;
- flood запросами;
- logout во время запроса;
- выключение модуля или addon-интерфейса конфигурацией.

### Клиентские проверки

- чистый клиент без `SavedVariables`;
- `/reload` при открытом окне;
- медленное получение item info;
- отсутствующий item в клиентском cache/DBC;
- коллекция больше одной страницы;
- быстрые переключения слотов и страниц;
- ввод кириллицы в поиск;
- несовместимая версия сервера;
- потерянный или пришедший не по порядку чанк;
- повторное нажатие кнопки применения;
- работа на целевой HD-сборке и обычном клиенте 3.3.5a.

### Регрессия

- существующее gossip-меню;
- vendor interface;
- `.transmog sync`;
- применение и удаление комплектов;
- portable NPC;
- автоматическое добавление внешностей в коллекцию;
- сохранение трансмогрификации после relog/restart.

## 15. Критерии готовности MVP

MVP считается готовым, если:

- аддон открывается при взаимодействии с NPC;
- клиент и сервер проверяют совместимость версии;
- список содержит только доступные и совместимые внешности;
- поиск и пагинация работают на большой коллекции;
- предпросмотр работает на целевом HD-клиенте либо явно отключён после теста;
- применение и удаление проходят только после полной серверной валидации;
- повторный запрос не приводит к двойному списанию;
- игрок без аддона может пользоваться старым gossip-интерфейсом;
- после relog внешний вид сохраняется;
- в обычном чате нет технических сообщений протокола;
- установка аддона и серверная конфигурация документированы.

## 16. Порядок первого рабочего инкремента

Первый инкремент рекомендуется ограничить следующими задачами:

1. Проверить `DressUpModel` на HD-клиенте.
2. Добавить каркас аддона и handshake.
3. Открывать пустое окно аддона от NPC с gossip fallback.
4. Получать одну страницу внешностей для одного выбранного слота.
5. Показывать иконки и локальный предпросмотр.
6. Применять и удалять одну внешность с полной серверной проверкой.

Такой вертикальный срез проверит все рискованные части решения до разработки
расширенного UI, комплектов и дополнительных фильтров.
