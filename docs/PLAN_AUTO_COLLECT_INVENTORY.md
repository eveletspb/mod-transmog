# План: автоматический сбор обликов из инвентаря

Дата: 2026-08-02
Ветка: `sbol/collect-inventory-appearances`
Статус: реализовано, объектная компиляция пройдена 2026-08-02.

## Краткое решение

Добавить опциональный автоматический сбор подходящих обликов из рюкзака и экипированных сумок без необходимости надевать предмет.

Рекомендуемая реализация:

- использовать `PLAYERHOOK_ON_STORE_NEW_ITEM` как основной триггер;
- не разыменовывать и не сохранять `Item*`, переданный в hook;
- синхронно сканировать актуальные слоты инвентаря через `Player::GetItemByPos`;
- для каждого слота повторно получать текущий предмет и обрабатывать его только внутри текущего вызова;
- вынести существующую логику `.transmog claim` в общий безопасный метод и переиспользовать её в команде и автоматическом сборщике;
- привязывать автоматически собранные BOE-предметы к персонажу;
- пропускать refundable и временно BoP-tradeable предметы;
- выполнять сканирование при login, чтобы обработать уже лежащие в сумках предметы;
- добавить настройку `Transmogrification.AutoCollectInventoryAppearances`, по умолчанию включённую.
- добавить настройку `Transmogrification.AutoCollectBindItems`, по умолчанию включённую;
- разрешить владельцу сервера отключить привязку, явно задокументировав возможность многократного открытия одного BOE-предмета на разных аккаунтах.

Схема БД не меняется: используется существующая таблица `custom_unlocked_appearances`.

## Цель

Игрок должен получить внешний вид подходящего предмета, когда предмет находится в его рюкзаке или экипированной сумке. Надевать предмет и вручную выполнять `.transmog claim` не требуется.

Фича должна:

- работать только при включённой системе коллекций;
- учитывать текущие ограничения трансмогрификации;
- не позволять открывать один BOE-облик нескольким аккаунтам через передачу одного предмета;
- не ломать возврат недавно купленных предметов;
- не ломать временную передачу BoP-добычи другим участникам рейда;
- безопасно сосуществовать с auto-sell и inventory management модулями;
- не обращаться к предмету после его удаления или продажи.

## Не входит в задачу

- изменение правил совместимости source/target;
- изменение схемы коллекций;
- сбор предметов из банка в реальном времени;
- сбор предметов непосредственно из почты до помещения в сумку;
- изменение логики auto-sell модулей;
- гарантированный сбор предмета, который другой модуль синхронно уничтожил до запуска callback `mod-transmog`;
- сохранение неподходящих предметов только ради возможного будущего изменения конфигурации.

## Текущее состояние

Сейчас модуль добавляет облики через:

- `OnPlayerEquip`;
- loot/create/store hooks, но только для BoP или уже soulbound предметов;
- награды заданий;
- одноразовую ретроактивную проверку;
- ручную команду `.transmog claim`.

Команда `.transmog claim` уже содержит правильные базовые действия для предмета из сумки:

1. Проверяет `SuitableForTransmogrification`.
2. Проверяет наличие облика в коллекции аккаунта.
3. Снимает refundable и tradeable-состояния.
4. Привязывает физический предмет.
5. Помечает item state изменённым.
6. Добавляет item entry в коллекцию.

Эта логика находится локально в `cs_transmog.cpp` и недоступна `PlayerScript`. Дублировать её нельзя — правила команды и автоматического сбора со временем разойдутся.

## Семантика автоматического сбора

### Подходящий предмет

Автоматический сбор должен требовать:

- `Transmogrification.UseCollectionSystem = 1`;
- `Transmogrification.AutoCollectInventoryAppearances = 1`;
- валидные `Player`, `WorldSession`, `Item` и `ItemTemplate`;
- отсутствие item entry в коллекции аккаунта;
- успешный `SuitableForTransmogrification(player, itemTemplate)`;
- отсутствие refundable-флага;
- отсутствие `ITEM_FIELD_FLAG_BOP_TRADEABLE`.

В отличие от существующего `AddToDatabase`, автоматический сбор не должен учитывать `TrackUnusableItems`. Требование задачи — собирать предметы, которые подходят для трансмогрификации сейчас.

### BOE-предметы

При `Transmogrification.AutoCollectBindItems = 1` подходящий непривязанный BOE-предмет автоматически привязывается к персонажу перед добавлением облика:

- `SetOwnerGUID`;
- `SetNotRefundable`;
- `ClearSoulboundTradeable`, если применимо;
- `SetBinding(true)`;
- `SetState(ITEM_CHANGED, player)`.

Это необходимо для защиты экономики: без привязки один физический предмет можно передавать между аккаунтами и открывать облик каждому из них.

При `Transmogrification.AutoCollectBindItems = 0` облик добавляется в постоянную коллекцию аккаунта, но физический предмет не изменяется:

- не вызывается `SetBinding(true)`;
- не меняется owner;
- не снимается refundable или BoP-tradeable состояние;
- предмет можно продать, передать, отправить почтой или выставить на аукцион, если это разрешено его обычными свойствами.

Это намеренно менее строгий серверный режим. Один BOE-предмет можно последовательно передать нескольким аккаунтам, и каждый аккаунт навсегда откроет его облик. Автоматически отозвать такой облик после потери предмета нельзя без отдельной модели владения и изменения схемы БД.

### Refundable-предметы

Автоматический режим пропускает refundable-предметы и не отменяет право возврата без явного действия игрока.

Ручная `.transmog claim` остаётся явным подтверждением и может сохранить текущее поведение — снять refundable и привязать предмет.

### Временно BoP-tradeable предметы

Автоматический режим пропускает предметы с grace period для передачи участникам рейда. Это предотвращает неожиданную потерю возможности передать добычу.

Игрок сможет:

- дождаться окончания периода и следующего inventory scan/login;
- явно использовать `.transmog claim`, принимая привязку предмета.

### Уже известный облик

Если облик уже есть в коллекции:

- предмет не привязывается;
- item state не изменяется;
- SQL не выполняется;
- сообщение игроку не отправляется.

## Выбор hooks

### Основной: `PLAYERHOOK_ON_STORE_NEW_ITEM`

Hook вызывается из `Player::StoreNewItem` после `StoreItem`, когда предмет уже находится в инвентаре.

Преимущества:

- охватывает обычную добычу и master loot;
- предмет уже доступен через инвентарь игрока;
- позволяет игнорировать потенциально опасный аргумент `Item*`;
- срабатывает до отложенной на `1 ms` продажи в известных `mod-junk-to-gold` и `mod-junk-to-gold-plus`;
- не требует таймеров и хранения указателей.

Callback должен иметь вид, эквивалентный:

```cpp
void OnPlayerStoreNewItem(Player* player, Item* /*item*/, uint32 /*count*/) override
{
    CollectInventoryAppearances(player);
}
```

Переданный `Item*` намеренно не используется.

### Дополнительный: `PLAYERHOOK_ON_LOGIN`

После загрузки персонажа выполняется scan рюкзака и экипированных сумок. Это покрывает:

- предметы, которые уже находились в инвентаре до включения настройки;
- предметы, пропущенные во время предыдущей версии модуля;
- предметы, которые стали подходящими после изменения требований или уровня персонажа.

Login scan не должен зависеть от одноразового `SETTING_RETROACTIVE_CHECK`, потому что пригодность предмета может измениться позже.

### Не использовать `PLAYERHOOK_ON_UPDATE`

Периодический scan на каждом update слишком дорогой и создаёт лишние обращения к инвентарю и collection cache.

### Не использовать отложенный callback с `Item*`

Нельзя захватывать `Item*`, `Bag*` или ссылку на предмет в `m_Events`, lambda, callback либо контейнер. К моменту выполнения предмет может быть продан, объединён со stack, перемещён или уничтожен.

Если позже понадобится отложенная обработка, допустимо хранить только:

- GUID игрока;
- GUID предмета;
- item entry;
- bag/slot как подсказку, но не как гарантию.

Перед обработкой объект необходимо заново разрешить через актуальный `Player`, затем проверить GUID/entry и все nullable-результаты.

Для текущей задачи отложенная обработка не нужна.

## Предлагаемая структура кода

### 1. Общий результат claim

Перенести `ClaimResult` из `cs_transmog.cpp` в область `Transmogrification`:

```cpp
enum class ClaimAppearanceResult
{
    Claimed,
    AlreadyOwned,
    Unsuitable,
    Refundable,
    Tradeable
};
```

При необходимости `Refundable` и `Tradeable` можно объединить в `TemporarilyUnavailable`, если вызывающему коду не нужно различать причины.

### 2. Общий метод обработки предмета

Добавить метод сервиса, например:

```cpp
ClaimAppearanceResult ClaimAppearance(
    Player* player,
    Item* item,
    bool explicitClaim);
```

`explicitClaim` определяет поведение для refundable и BoP-tradeable:

- `true` — текущее явное поведение команды: снять ограничения и привязать;
- `false` — безопасный auto mode: пропустить временно ограниченный предмет.

Политика привязки определяется отдельно:

- explicit claim сохраняет текущее поведение и всегда привязывает заявленный предмет;
- automatic claim привязывает предмет только при `AutoCollectBindItems = 1`;
- automatic claim при `AutoCollectBindItems = 0` не изменяет состояние предмета.

Метод используется только синхронно. Он не сохраняет `Item*` и не вызывает отложенные callbacks.

Альтернатива — два явно названных метода поверх одного private helper. Она безопаснее читается, но добавляет немного boilerplate. Рекомендуемый вариант — один метод с небольшим enum policy вместо `bool`, если итоговая сигнатура остаётся понятной:

```cpp
enum class ClaimMode { Explicit, Automatic };
```

### 3. Сканирование инвентаря

Добавить private helper в `PS_Transmogrification` либо сервис:

```cpp
void CollectInventoryAppearances(Player* player);
```

Сканировать только:

- `INVENTORY_SLOT_ITEM_START .. INVENTORY_SLOT_ITEM_END`;
- содержимое `INVENTORY_SLOT_BAG_START .. INVENTORY_SLOT_BAG_END`.

Не сканировать:

- экипированные предметы — их уже покрывает `OnPlayerEquip`;
- bank slots — банк не является текущим инвентарём задачи;
- keyring/buyback/mail/auction storage.

Для каждого слота:

1. Получить текущий `Item*` через `GetItemByPos`.
2. Немедленно проверить `nullptr`.
3. Получить и проверить `ItemTemplate const*`.
4. Обработать предмет синхронно.
5. Не использовать указатель после перехода к следующему слоту.

Рекомендуется сначала проверять collection cache по `item entry`, чтобы не выполнять дорогую полную проверку и не изменять уже известный предмет.

### 4. Команда `.transmog claim`

Заменить локальный `TryClaimItem` вызовом общего сервиса. Пользовательские сообщения и подсчёт `claim all` оставить в `cs_transmog.cpp`.

Это обеспечивает одинаковые правила пригодности и привязки для ручного и автоматического пути.

### 5. Конфигурация

Добавить в `conf/transmog.conf.dist`:

```ini
#
#    Transmogrification.AutoCollectInventoryAppearances
#        Description: Automatically binds eligible items in the player's bags and adds their
#                     appearances to the account collection without requiring the item to be equipped.
#                     Refundable and temporarily BoP-tradeable items are skipped.
#        Default:     1
#
Transmogrification.AutoCollectInventoryAppearances = 1
```

Добавить вторую настройку:

```ini
#
#    Transmogrification.AutoCollectBindItems
#        Description: Bind eligible BOE items when their appearances are automatically collected.
#                     Disable only if the server intentionally allows the same tradeable item to
#                     permanently unlock its appearance for multiple accounts.
#                     This setting affects automatic collection only; explicit `.transmog claim`
#                     continues to bind the claimed item.
#        Default:     1
#
Transmogrification.AutoCollectBindItems = 1
```

Обе настройки загружать в `Transmogrification::LoadConfig` и предоставить read-only getters.

Автосбор должен быть выключен автоматически, если `UseCollectionSystem = 0`.

`AutoCollectBindItems` не имеет эффекта при выключенном `AutoCollectInventoryAppearances`.

### 6. Логи и сообщения

Для успешно собранного облика использовать существующий `LANG_TRANSMOG_ADDED_APPEARANCE`.

Не отправлять сообщения для:

- уже известного облика;
- неподходящего предмета;
- refundable-предмета;
- временно tradeable-предмета.

Новые строки `module_string` не нужны, если не добавляется отдельная команда или пользовательское предупреждение.

## Защита от segmentation fault

### Обязательные правила реализации

- Не разыменовывать `Item*`, переданный в `OnPlayerStoreNewItem`.
- Не сохранять `Item*` или `Bag*` за пределами текущего синхронного scope.
- Не захватывать `Player*` или `Item*` в отложенную lambda.
- На каждой итерации заново получать предмет через `GetItemByPos`.
- Сразу проверять `Item*` и `ItemTemplate const*` на `nullptr`.
- Не обращаться к предмету после функции, которая может удалить, переместить или объединить его.
- До модификации предмета проверить, что он всё ещё принадлежит текущему игроку.
- Не полагаться на порядок регистрации модулей.
- Не выполнять рекурсивный inventory scan из hooks, которые вызываются самой привязкой или `SetState`.

### Почему это защищает от auto-sell

Известные `mod-junk-to-gold` и `mod-junk-to-gold-plus`:

- получают `Item*` в `OnPlayerLootItem`;
- сохраняют только `ObjectGuid`;
- откладывают продажу на `1 ms`;
- перед продажей заново вызывают `player->GetItemByGuid`;
- ничего не делают, если предмет уже отсутствует.

`mod-transmog` выполнит синхронный inventory scan в `OnPlayerStoreNewItem` до отложенного удаления. После выхода из callback никакой указатель на предмет не останется.

### Граница ответственности

Если сторонний модуль синхронно удаляет предмет внутри того же ScriptMgr hook, а затем другие callbacks получают уже висячий общий аргумент `Item*`, это дефект взаимодействия на уровне стороннего модуля/dispatcher. `mod-transmog` снижает риск, потому что игнорирует общий аргумент и читает только актуальное состояние `Player`.

Гарантировать сбор уже уничтоженного предмета невозможно. Корректное поведение в этом случае — пропустить предмет без падения.

## Риски совместимости с другими модулями

| Интеграция | Риск | Уровень | Митигация |
|---|---|---:|---|
| `mod-junk-to-gold` / `mod-junk-to-gold-plus` | Предмет продаётся через 1 ms после loot | Низкий | Синхронный scan в `OnStoreNewItem`, отсутствие сохранённых `Item*` |
| Другой синхронный auto-sell | Предмет удалён до callback transmog | Средний | Игнорировать hook `Item*`, сканировать только актуальные slots; допускается безопасный пропуск |
| Auto-vendor при разговоре с NPC | Массовое удаление содержимого сумок | Низкий | Нет активного deferred scan; следующий login обработает оставшиеся предметы |
| Auto-sort / reagent bank | Предмет меняет bag/slot | Низкий | Не кешировать позицию; получать предмет заново для каждой операции |
| Stack merge | Исходный экземпляр уничтожается при объединении | Низкий | Коллекция работает по item entry; не хранить GUID/указатель между callbacks |
| Mail / auction modules | Предмет сразу перемещается из inventory | Средний | Обрабатывать только предметы, реально найденные в сумках; не вмешиваться в mail/auction lifecycle |
| Trade modules | Автопривязка BOE запрещает дальнейшую передачу | Высокий, ожидаемый | Явно документировать семантику; feature toggle; не изменять уже известные предметы |
| Trade modules при `AutoCollectBindItems = 0` | Один BOE открывает постоянный облик нескольким аккаунтам | Высокий, осознанный | Предупреждение в config и README; безопасное значение по умолчанию `1` |
| Raid loot trading | Автосбор может отменить grace period | Высокий | Всегда пропускать `BOP_TRADEABLE` в automatic mode |
| Vendor refund | Автосбор может отменить возврат | Высокий | Всегда пропускать refundable в automatic mode |
| Inventory expansion/custom bags | Нестандартные диапазоны слотов | Средний | Использовать AzerothCore constants и фактический `Bag::GetBagSize()` |
| Несколько активных персонажей аккаунта | Одновременное изменение account cache | Средний | Сохранить текущую world-thread модель; отдельно проверить thread-safety `collectionCache` при map threading |
| Модули, слушающие item state/binding | Побочные callbacks или изменения поведения | Средний | Менять item state только для нового подходящего облика; тестировать отсутствие рекурсии |
| `TrackUnusableItems` | Сбор неподходящих предметов вопреки задаче | Средний | В automatic mode всегда явно вызывать `SuitableForTransmogrification` |
| Transmog Plus | Серые/legendary становятся подходящими по подписке | Средний | Использовать существующие проверки eligibility; тестировать с Plus on/off |

## Производительность

Полный scan рюкзака и четырёх сумок — ограниченное количество слотов, но hook может вызываться часто при массовой добыче.

Базовая реализация остаётся простой:

- ранний выход при выключенной настройке или коллекции;
- ранняя проверка collection cache;
- отсутствие SQL для известных обликов;
- отсутствие периодического `OnUpdate` scan.

Если профилирование покажет проблему при массовом loot, допустимая оптимизация второго этапа:

- coalescing нескольких событий в один scan;
- хранить только pending player GUID;
- выполнять scan в безопасной точке update;
- не хранить raw pointers.

Но deferred/coalesced вариант может проиграть гонку auto-sell и поэтому не рекомендуется без измеренной необходимости.

## Пошаговый план реализации

1. Добавить `AutoCollectInventoryAppearances` и `AutoCollectBindItems` в конфигурацию, состояние singleton и getters.
2. Перенести `ClaimResult` и claim-логику из `cs_transmog.cpp` в общий API `Transmogrification`.
3. Добавить режим `Explicit`/`Automatic` для разного поведения refundable и BoP-tradeable предметов.
4. Перевести `.transmog claim`, `.transmog claim all` и claim по bag/slot на общий API.
5. Добавить `PLAYERHOOK_ON_STORE_NEW_ITEM` в список enabled hooks `PS_Transmogrification`.
6. Реализовать синхронный `CollectInventoryAppearances(Player*)`, не использующий hook `Item*`.
7. Вызвать scan из `OnPlayerStoreNewItem`.
8. Вызвать scan при login независимо от one-time retroactive flag, но только при включённой настройке.
9. Убедиться, что текущие equip/loot/create hooks не создают повторные сообщения и SQL.
10. Обновить документацию после реализации:
    - описать оба параметра и их взаимодействие в `conf/transmog.conf.dist`;
    - добавить пользовательский раздел автоматического сбора в `README.md`;
    - обновить `docs/MODULE_CONTEXT.md` как технический контекст;
    - отдельно предупредить, что `AutoCollectBindItems = 0` позволяет одному BOE-предмету открыть постоянный облик нескольким аккаунтам.
11. Выполнить сборку AzerothCore с модулем.
12. Выполнить ручную интеграционную тестовую матрицу.

## Тестовая матрица

### Основные сценарии

1. Поднять подходящий BOE-предмет:
   - облик добавлен;
   - предмет остаётся в сумке;
   - предмет привязан;
   - повторного SQL/message нет.
2. Получить подходящий BoP-предмет:
   - облик добавлен без экипировки.
3. Получить неподходящий предмет:
   - облик не добавлен;
   - предмет не изменён.
4. Получить уже известный предмет:
   - предмет не привязывается автоматически;
   - сообщение не отправляется.
5. Перезайти с подходящим BOE в сумке:
   - login scan добавляет облик и привязывает предмет.
6. Выключить настройку:
   - старое поведение сохранено;
   - `.transmog claim` продолжает работать.
7. Выключить collection system:
   - auto collector ничего не делает.
8. Установить `AutoCollectBindItems = 0`:
   - подходящий BOE открывает облик;
   - предмет не привязывается и не изменяет owner/state;
   - предмет остаётся доступен для обычной торговли и аукциона.

### Экономика и trading

9. Купить refundable-предмет у vendor:
   - auto collector его пропускает;
   - возврат остаётся доступен.
10. Выполнить явный `.transmog claim` refundable-предмета:
   - облик добавлен;
   - право возврата снято.
11. Получить BoP-tradeable рейдовую добычу:
    - auto collector пропускает предмет;
    - передача остаётся доступна.
12. Выполнить явный claim BoP-tradeable предмета:
    - предмет привязан окончательно;
    - облик добавлен.

### Совместимость с auto-sell

13. Включить `mod-junk-to-gold` и разрешить серые предметы для transmog:
    - облик добавляется до auto-sell;
    - предмет затем продаётся;
    - worldserver не падает.
14. Включить `mod-junk-to-gold-plus`:
    - результат аналогичен;
    - отсутствует use-after-free.
15. Смоделировать отсутствие предмета при scan:
    - слот возвращает `nullptr`;
    - обработка продолжается без ошибки.
16. Переместить/продать предмет сразу после loot:
    - нет сохранённого `Item*`;
    - нет segmentation fault.

### Регрессия

17. Обычная трансмогрификация через Gossip.
18. Обычная трансмогрификация через Fake Vendor.
19. `.transmog claim`, `claim all`, claim по bag/slot.
20. Явный `.transmog claim` продолжает привязывать предмет при `AutoCollectBindItems = 0`.
21. Пресеты, скрытие и удаление внешнего вида.
22. Retroactive quest/inventory collection.
23. Transmog Plus с серыми и legendary предметами.

## Критерии готовности

- Подходящий предмет из сумки открывает облик без экипировки.
- При `AutoCollectBindItems = 1` новый BOE-предмет привязывается до добавления облика.
- При `AutoCollectBindItems = 0` новый BOE-предмет открывает облик без изменения предмета.
- Refundable и временно BoP-tradeable предметы не меняются automatic mode.
- Уже известные предметы не привязываются и не пишутся повторно в БД.
- Код автоматического сбора не использует `Item*` из hook.
- Нет raw pointers в отложенных callbacks или runtime-кешах фичи.
- Совместная проверка с обоими junk-to-gold модулями проходит без падения.
- Сборка AzerothCore проходит.
- `transmog.conf.dist`, README и локальный `MODULE_CONTEXT.md` описывают оба параметра и риск режима без привязки.

## Зафиксированное продуктовое решение

Оба параметра включены по умолчанию:

```ini
Transmogrification.AutoCollectInventoryAppearances = 1
Transmogrification.AutoCollectBindItems = 1
```

Владелец сервера может установить `AutoCollectBindItems = 0`, принимая риск многократного постоянного открытия одного BOE-предмета на разных аккаунтах. Явная команда `.transmog claim` независимо от этой настройки продолжает привязывать предмет.
